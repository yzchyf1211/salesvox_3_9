## 1. AOM（层级对象模型）

### 1.1 定义

AOM（Activity Object Model）是整个演绎流程的**层级骨架**。它定义了从大到小、从粗到细的任务嵌套结构。每一层是一个独立的 LangGraph 子图，父层通过 `_builtin_start_task` 阻塞调用子层，形成递归嵌套。

### 1.2 代码结构

每个 AOM 层级对应一个 Middleware 类：

```python
# 基类: agentickit/prosonaagent/core/middleware/task_middleware.py
class TaskMiddleware(AgentMiddleware):
    task_group_name: str              # 本层标识（如 "project"）
    sub_task_group_name: Optional[str] # 子层标识（如 "activity"），叶子层为 None
    state_schema: type                # 本层状态类型（TypedDict）
    allow_sub_tasks: bool             # 是否允许创建子任务（叶子层为 False）
    skills: List[str]                 # 本层需要的 Skill 名称列表
    tools: List[Any]                  # 本层绑定的 Tool 列表

# 增强基类（支持 Card 展示）:
# agentickit/prosonaagent/core/middleware/enhance_task_middleware.py
class EnhanceTaskMiddleware(TaskMiddleware):
    # 自动加入 _builtin_send_user_content 工具
    # 拦截该工具调用 → 调 handler.aget_card() → 发送 A2A 展示消息
```

每个 AOM 层级还对应一个 State 类（TypedDict 继承链）：

```python
# agentickit/prosonaagent/aom/state.py
class RootTaskState(TaskState):       # Level 0，加 project_id
class ProjectTaskState(RootTaskState): # Level 1，加 module_list, activity_list
class ActivityTaskState(ProjectTaskState): # Level 2，加 activity, sco_list
class SCOTaskState(ActivityTaskState): # Level 3，加 sco, sco_segment_list, order
```

框架自动继承的基础字段（TaskState）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `Optional[str]` | 当前任务 ID |
| `name` | `Optional[str]` | 当前任务名 |
| `status` | `Optional[str]` | `pending` / `running` / `paused` / `completed` / `interrupted` / `recovering` |
| `params` | `Optional[dict]` | 启动参数（`start_task` 时传入） |
| `sub_tasks` | `List[str]` | 子任务 ID 列表 |
| `result` | `Optional[Dict[str, Any]]` | 结束时的结果数据 |
| `mode` | `Optional[str]` | `"start"` 或 `"recover"` |
| `messages` | `list[AnyMessage]` | 消息列表（继承自 AgentState） |
| `context_id` | `str` | 会话 ID |
| `user_profile` | `Optional[UserProfile]` | 用户信息 |
| `locale` | `Optional[str]` | 语言代码 |

### 1.3 包含什么

一个 AOM 层级的设计需要定义：

- **层级标识**：`task_group_name` 和 `sub_task_group_name`
- **状态字段**：本层在父层基础上新增哪些 TypedDict 字段
- **引用的实体类型**：状态字段中引用的 Schema（TypedDict）结构
- **生命周期行为**：`abefore` / `apause` / `aresume` / `ainterrupt` / `arecover` / `aafter` 各自做什么
- **绑定的 Skill 和 Tool**：本层级别通用的能力

### 1.4 设计重点

AOM 的核心在于**层级划分**——你的业务场景从大到小自然分成几层？每一层管理什么粒度的事情？

设计原则：
- 每一层只关心"本层的标准动作"（加载数据、注入上下文、发通知），具体业务逻辑交给 Task Handler
- 状态字段只放"需要向下透传给子层"的数据
- Root 层永不结束，是会话的容器
- 叶子层（`allow_sub_tasks=False`）不再往下分，业务差异由 Task Handler 接管

### 1.5 生命周期方法签名

所有 AOM 层的生命周期方法签名统一：

```python
async def abefore(self, state, runtime) -> Dict[str, Any]   # 进入
async def apause(self, state, runtime) -> Dict[str, Any]     # 暂停
async def aresume(self, state, runtime) -> Dict[str, Any]    # 恢复
async def ainterrupt(self, state, runtime) -> Dict[str, Any] # 中断
async def arecover(self, state, runtime) -> Dict[str, Any]   # 从中断恢复
async def aafter(self, state, runtime) -> Dict[str, Any]     # 正常结束
```

返回值是**增量 Dict**，框架自动 merge。其中 `messages` 字段追加，其他字段覆盖。

### 1.6 设计模板

```
层级名（task_group_name）:     ___
子层（sub_task_group_name）:   ___
父类:                          TaskMiddleware | EnhanceTaskMiddleware
是否叶子（allow_sub_tasks）:   true | false
状态类名:                      ___TaskState
继承自:                        ___TaskState

新增状态字段:
  - 字段名: 类型               # 说明

生命周期:
  abefore:
    加载数据:  ___
    注入上下文: ___
    发送通知:  ___
  apause:   ___
  aresume:  ___
  ainterrupt: ___
  arecover: ___
  aafter:   ___

绑定 Skills:  [skill_name_1, skill_name_2]
绑定 Tools:   [tool_name_1, tool_name_2]
```

### 1.7 引用实体类型模板

当状态字段引用非基础类型时，需同时定义：

```
类型名:   XxxSchema（TypedDict）
字段:
  - 字段名: 类型    # 说明
```

## 2. Task（任务处理器）

### 2.1 定义

Task 是**叶子层不同业务类型的具体实现**。如果说 AOM 是纵向的层级骨架，Task 就是挂在叶子节点上的横向分类。同一个 AOM 叶子层（比如 SCO 层）可以有多种 Task 类型（问答题、视频、总结），每种 Task 有不同的业务逻辑、不同的上下文、不同的展示方式。

### 2.2 代码结构

每种 Task 类型对应一个 Handler 类：

```python
# 基类: agentickit/prosonaagent/core/handler/task_handler.py
class TaskHandler(Generic[StateT]):
    name: Optional[str]           # 注册名，格式 "{group}:{type}"
    state_schema: type            # 扩展状态（在叶子层 State 基础上加字段）
    skills: List[str]             # 本 Task 需要的 Skill
    tools: List[Any]              # 本 Task 需要的 Tool
    model_group: Optional[str]    # 使用的模型组（默认 "main"）

# 增强基类（支持 Card 渲染）:
# agentickit/prosonaagent/core/handler/enhance_task_handler.py
class EnhanceTaskHandler(TaskHandler[StateT]):
    async def aget_card(self, state, action, params) -> Optional[AOMCard]
```

Handler 通过 `name` 注册到 `HandlerRegistry`，框架按名称路由：

```
查找顺序: "{group}:{type}" → "{group}" → "general"
示例:     "sco:quiz" → "sco" → "general"
```

### 2.3 包含什么

一个 Task 的设计需要定义：

- **注册名（name）**：`"{叶子层group}:{任务类型}"`，如 `"sco:quiz"`
- **扩展状态字段**：在叶子层 State 基础上增加的字段
- **Task Prompt**：该任务类型的行为指令（存放在 Langfuse，§2.7 详述）
- **Skill 列表**：该任务需要的 Skill（与 Middleware 层的 skills 合并去重）
- **Tool 列表**：该任务需要的 Tool（与 Middleware 层的 tools 合并去重）
- **生命周期行为**：各钩子中的业务逻辑
- **Card 渲染逻辑**：`aget_card` 支持哪些 action，每个 action 返回什么 Card

### 2.4 设计重点

Task 的核心在于**分而治之**——把一个演绎过程中的不同流程环节识别出来，每种环节有自己独立的：
- 进入时需要的业务数据和上下文
- 交互过程中的工具和能力
- 结束时的收尾动作（评分、上报、生成报告等）
- 面向用户的展示形态（Card）

设计时先不要急着写具体 prompt 内容，先把**有几种 Task、每种的职责边界、进入/退出做什么**想清楚。

### 2.5 生命周期方法

当前任务级：

```python
async def abefore(self, state, runtime) -> Dict | None     # 任务启动
async def apause(self, state, runtime) -> Dict | None       # 任务暂停
async def aresume(self, state, runtime) -> Dict | None      # 任务恢复
async def ainterrupt(self, state, runtime) -> Dict | None   # 任务中断
async def arecover(self, state, runtime) -> Dict | None     # 从中断恢复
async def aafter(self, state, runtime) -> Dict | None       # 任务正常结束
```

子任务级（当该 Handler 所在层有子任务时）：

```python
async def abefore_task(self, state, runtime, sub_task_id, sub_task_name) -> Dict | None
async def aafter_task(self, state, runtime, sub_state) -> Dict | None
async def ainterrupt_task(self, state, runtime, sub_state) -> Dict | None
```

其他：

```python
async def aafter_user_input(self, state, runtime, user_input, action, params) -> Dict | None
async def awrap_model_call(self, request, handler) -> ModelCallResult
async def awrap_tool_call(self, request, handler) -> ToolMessage | Command
```

### 2.6 设计模板

```
Handler 类名:        ___TaskHandler
注册名（name）:      "group:type"（如 "sco:quiz"）
父类:                TaskHandler | EnhanceTaskHandler
模型组（model_group）: "main"（默认）

扩展状态:
  状态类名:  ___TaskState
  继承自:    ___TaskState（叶子层的 State）
  新增字段:
    - 字段名: 类型    # 说明

Skills:  [skill_name_1, ...]
Tools:   [tool_name_1, ...]

生命周期:
  abefore:
    加载:    ___
    注入:    ___（abefore 中注入什么 SystemMessage 给 LLM）
  aafter:    ___
  aresume:   ___
  其他:      ___

Card 渲染（aget_card）:
  支持的 action:
    - "action_name_1": 什么时候触发，返回什么 Card
    - "action_name_2": ...

用户输入处理（aafter_user_input）:
  - action="xxx": 做什么
```

### 2.7 Task Prompt

每种 Task 类型有一份专属的行为指令 prompt。

**存储方式**：Langfuse，key 为 `{path}/{handler.name}/TASK.md`

**加载时机**：`TaskMiddleware.abefore()` 中自动调用 `get_task_prompt(name=handler.name)`，注入为 SystemMessage

**配置来源**（Nacos `application.toml`）：

```toml
[[prompts.tasks.locations]]
id = "prosona"
namespace = "prosona"
path = "tasks"
tasks = ["root", "project", "activity", "sco", "sco:quiz", "sco:lecture_summary"]
```

**设计格式**：

```
Task Prompt 名称:    与 handler.name 一致（如 "sco:quiz"）
Langfuse key:        {path}/{name}/TASK.md（如 "tasks/sco:quiz/TASK.md"）

--- Prompt 内容（Markdown）---

（这里是给 LLM 看的任务行为指令，内容包括：
 - 你正在做什么任务
 - 目标是什么
 - 步骤/流程
 - 结束条件：什么时候调 end_task
 - 可用的 action（如果有 Card）
 - 注意事项）
```

## 3. Skill（技能知识）

### 3.1 定义

Skill 是**给 LLM 看的知识文档**，不是可执行的代码。它是 Markdown 格式的方法论、流程指南、领域知识，通过上下文注入让 LLM 知道"怎么做某件事"。

**Skill ≠ Tool**。Tool 是 LLM 可以调用的函数（有参数、会执行、返回结果）。Skill 是 LLM 可以阅读的文档（有方法论、有步骤、指导行为）。

### 3.2 代码结构

Skill 由 `agentickit.core.infra.skills` 模块管理（外部包 `agentickit`），不在本仓库内。

**Skill 对象结构**：

```python
# agentickit.core.infra.skills.types
class Metadata:
    name: str           # 技能名称（如 "manage_task"）
    description: str    # 一句话描述

class Skill:
    metadata: Metadata  # 元数据
    body: str           # Markdown 正文
```

**加载与使用**：

```python
from agentickit.core.infra.skills.manager import get_skills_by_names

skills = get_skills_by_names(["manage_task", "review"])
```

**Skill 在系统中的三种呈现方式**（渐进式披露）：

| 呈现方式 | 时机 | 代码位置 | LLM 看到什么 |
|---------|------|---------|-------------|
| 元数据摘要 | 每次模型调用 | `ModelEnhanceMiddleware` | Skill 列表：名称 + 一句话描述 |
| 全文注入 | 任务启动时 | `TaskMiddleware.abefore()` | 完整 Markdown 正文（作为 SystemMessage） |
| 按需查阅 | LLM 主动调用 | `_builtin_get_skill_information` 工具 | 完整 Skill 内容 |

**Skill 资源文件**：Skill 可以附带资源文件（如参考文档、脚本），通过 `_builtin_get_skill_resource(name, path)` 按需读取。

### 3.3 声明方式

在 Middleware 和 Handler 中通过 `skills` 列表声明：

```python
class SCOMiddleware(EnhanceTaskMiddleware):
    skills = ["manage_task"]    # Middleware 层级的通用 Skill

class QuizTaskHandler(EnhanceTaskHandler):
    skills = ["quiz_guide"]     # Handler 特有的 Skill
```

框架会自动合并 Middleware.skills + Handler.skills（去重）。

### 3.4 设计重点

Skill 的重点**不在于格式**（就是 Markdown），而在于：

- **与 Task 的区分**：Task Prompt 告诉 LLM "你现在在做什么任务"，Skill 告诉 LLM "做这类事情的方法论"。一个 Skill 可以被多个 Task 共享。
- **通用性设计**：好的 Skill 是跨任务复用的能力（如"如何管理任务生命周期"、"如何引导用户思考"、"如何做销售提问"），而不是某个具体任务的步骤。
- **方法论的独到见解**：Skill 的价值在于里面的方法论——如何提问、如何引导、如何判断时机。这部分需要领域专家的深度思考。

### 3.5 设计模板

```
Skill 名称（name）:      ___（如 "interest_probing"）
一句话描述（description）: ___（如 "通过提问探测客户兴趣点的方法论"）
使用者:                   哪些 Middleware / Handler 的 skills 列表中声明了它

附属资源文件（可选）:
  - path: 文件路径       # 说明

--- Skill 正文（Markdown）---

（这里是方法论内容。可以包括：
 - 核心理念
 - 步骤/流程
 - 判断标准
 - 话术示例
 - 注意事项
 - 常见错误

格式自由，本质就是一篇 Markdown 文档。
关键是里面的方法论要有独到见解。）
```

### 3.6 Skill 正文被注入后 LLM 看到的格式

```markdown
---
name: interest_probing
description: 通过提问探测客户兴趣点的方法论
---

（正文内容）

---

The above are the information of the `interest_probing` skill.
```

## 4. Tool（可执行工具）

### 4.1 定义

Tool 是 LLM **可以主动调用的可执行函数**。LLM 根据工具的名称和描述决定什么时候调用，调用时传入参数，框架执行函数并返回结果（Tool Call Result）。

**Tool ≠ Skill**。Tool 执行动作（调 API、修改状态、发消息），Skill 提供知识（方法论、指南）。

### 4.2 代码结构

每个 Tool 是一个 `@tool` 装饰的 async 函数：

```python
# langchain_core.tools.tool
@tool
async def tool_name(
    arg1: str,                           # 参数（LLM 填入）
    arg2: Optional[int] = None,          # 可选参数
    tool_runtime: ToolRuntime = None,    # 框架注入，不暴露给 LLM
) -> Command:
    """
    工具描述（这段 docstring 会被 LLM 看到，据此决定何时调用）

    Args:
        arg1: 参数1说明（LLM 看到）
        arg2: 参数2说明（LLM 看到）
    """
    tool_call_id = tool_runtime.tool_call_id  # 本次调用 ID
    state = tool_runtime.state                # 当前完整 state

    # ... 业务逻辑 ...

    return Command(update={
        "messages": [ToolMessage(
            content=build_tool_call_success_system_feedback("结果文本"),
            tool_call_id=tool_call_id,
        )],
        # 可选: 修改 state 字段
        # "field_name": new_value,
    })
```

### 4.3 包含什么

一个 Tool 的设计需要定义两部分：

**参数设计**（LLM 看到的接口）：
- 函数名：LLM 调用时使用的名称
- docstring：LLM 看到的描述（决定何时调用）
- 参数列表：名称、类型、说明

**行为设计**（函数体内的逻辑）：
- 执行什么操作（调 API、查数据、计算等）
- 返回什么 Tool Call Result（通过 ToolMessage content 反馈给 LLM）
- 是否修改 state（通过 `Command(update={...})`）
- 是否触发中断等待用户输入（通过 `interrupt(...)`）

### 4.4 设计重点

Tool 的重点**不在于单个工具的参数和函数怎么写**（那是研发的事），而在于**整体的工具体系设计**：

- 这个演绎角色需要哪些"手脚"？
- 每个工具的职责边界在哪——什么该是一个工具，什么该拆成两个？
- 哪些工具是通用的（挂在 Middleware），哪些是特定 Task 独有的（挂在 Handler）？
- 工具之间的协作关系：A 工具的结果是否是 B 工具的前置条件？

### 4.5 框架内置 Tool

以下 Tool 由框架提供，不需要设计：

| 工具名 | 参数 | 说明 | 自动可用条件 |
|--------|------|------|-------------|
| `_builtin_start_task` | `name: str, params: Optional[dict]` | 启动子任务 | `allow_sub_tasks=True` 的层 |
| `_builtin_end_task` | `is_interrupt: bool, result: Optional[dict]` | 结束当前任务 | 所有层 |
| `_builtin_recover_task` | `task_id: str, task_name: str` | 恢复被中断的任务 | `allow_sub_tasks=True` 的层 |
| `_builtin_get_skill_information` | `name: str` | 查阅 Skill 全文 | 所有层 |
| `_builtin_get_skill_resource` | `name: str, path: str` | 读取 Skill 资源文件 | 所有层 |
| `_builtin_send_user_content` | `action: str, params: Optional[dict]` | 展示内容给用户（触发 Card） | `EnhanceTaskMiddleware` 的层 |

以下 Tool 由框架提供但需要**手动声明**到 `tools` 列表中：

| 工具名 | 参数 | 说明 |
|--------|------|------|
| `_builtin_conversation` | `text: str, ask_question: bool` | 与用户对话。`ask_question=True` 时暂停等用户回复 |
| `_builtin_write_scratchpad` | `text: str` | 写草稿本（Agent 记录思路，用户看不到） |

### 4.6 Tool 的三种行为模式

| 模式 | 说明 | 代码特征 |
|------|------|---------|
| **纯返回** | 执行逻辑，结果反馈给 LLM | 只返回 `ToolMessage` |
| **修改状态** | 执行逻辑 + 改 state 字段 | `Command(update={"field": value, "messages": [...]})` |
| **暂停等待** | 暂停 Agent，等用户输入 | 调用 `interrupt(...)` |

### 4.7 设计模板

```
工具名（函数名）:    ___
描述（docstring）:   ___（这句话决定 LLM 何时调用，要精确）
注册位置:            Middleware.tools / Handler.tools / 哪个具体的类

参数:
  - 参数名: 类型     # 说明（给 LLM 看）

行为模式:            纯返回 | 修改状态 | 暂停等待

Tool Call Result（返回给 LLM 的反馈文本）:
  成功: "___"
  失败: "___"

状态修改（如有）:
  - state.field_name = ___

副作用（如有）:
  - 调用外部 API: ___
  - 写入存储: ___
```

## 5. Card（展示卡片）

### 5.1 定义

Card 是**发送给前端渲染的结构化数据**。当 LLM 判断需要"给用户展示一个东西"时，它调用 `_builtin_send_user_content(action, params)`，框架拦截后调用 Handler 的 `aget_card()` 方法，拿到 Card 数据，发送 A2A 消息给前端渲染。

### 5.2 代码结构

```python
# agentickit/prosonaagent/aom/types.py
class AOMCard(TypedDict, total=False):
    id: str                                            # 必填. 卡片标识
    name: str                                          # 必填. 卡片显示名称
    type: Literal["content", "record", "report"]       # 必填. 卡片类型
    data: dict | AOMCardRecordData | AOMCardReportData  # 必填. 给前端渲染的数据
    description: str                                   # 可选. 给 LLM 的反馈文本
    ext: Dict[str, Any]                                # 可选. 业务扩展字段
```

构建辅助函数：

```python
# agentickit/prosonaagent/aom/card.py
build_content_card(id, name, content: dict, description)  # type="content"
build_record_card(id, name, sco_id, sco_order, description)  # type="record"
build_report_card(id, name, artifact_id, description)     # type="report"
```

### 5.3 包含什么

一个 Card 的设计需要定义：

- **触发条件**：对应 `_builtin_send_user_content` 的 `action` 值
- **卡片元信息**：`id`、`name`、`type`
- **data 结构**：给前端渲染用的字段
- **description**：展示后反馈给 LLM 的文本——LLM 看到这段文字后知道"用户现在看到了什么"，据此接话

### 5.4 设计重点

Card 的核心不在于字段怎么定义（那是前端的事），而在于：

- `description` 的设计：这是**LLM 与前端展示之间的桥梁**。LLM 看不到前端画面，它只能通过 description 知道"用户现在看到了什么"，然后决定接下来说什么。description 写得好不好，直接影响 LLM 的接话质量。
- `action` 的划分：一个 Task 有几种展示形态？每种在什么时机触发？action 的名称要让 LLM 通过 Task Prompt 中的说明能理解。

### 5.5 description 的作用流程

```
LLM 调用 _builtin_send_user_content(action="display_question")
  → 框架调用 handler.aget_card(state, "display_question", params)
  → Handler 返回 AOMCard（含 description）
  → 框架发送 data 给前端渲染
  → 框架把 description 包装成 ToolMessage 反馈给 LLM:
    "user can see the content: {description}"
  → LLM 据此决定接下来说什么
```

### 5.6 设计模板

```
卡片 ID（id）:           ___
卡片名称（name）:        ___
卡片类型（type）:        content | record | report
触发 action:             ___（LLM 调用 _builtin_send_user_content 时传的 action 值）
所属 Task:               ___（哪个 Handler 的 aget_card 返回这个 Card）

data 结构（给前端）:
  - 字段名: 类型          # 说明

description（给 LLM 的反馈）:
  "___"
  或引用 Langfuse 模板: key + 变量列表

ext（可选，业务扩展）:
  - 字段名: 类型          # 说明
```

## 6. System Prompt（全局人设）

### 6.1 定义

System Prompt 是 Agent 的**全局角色定义**，是 LLM 每次被调用时都会看到的底层设定。它定义了"你是谁"、"你的职责是什么"、"有哪些约束"，但不涉及具体某个任务的步骤。

### 6.2 代码结构

```python
# __main__.py
SYSTEM_PROMPT = """..."""

# 传入
graph, _ = create_prosona_agent(
    system_prompt=SYSTEM_PROMPT,
    ...
)
```

全局唯一，所有 AOM 层级、所有 Task 类型共享同一份 System Prompt。

### 6.3 包含什么

- **角色（Role）**：一句话定义职能
- **人设（Persona）**：名字、性格、说话风格
- **任务（Task）**：宏观职责描述（编排 + 执行）
- **约束（Constraints）**：场景限制、行为边界、输出格式

### 6.4 设计重点

- **简洁**：这段文字每次模型调用都会带上，越长越费 token
- **不写具体任务步骤**：那是 Task Prompt 的事
- **约束要明确**：什么能做、什么不能做，边界清晰

### 6.5 设计模板

```markdown
# Role
（一句话角色定义）

# Persona
（名字、性格特点、说话风格）

# Task
（宏观任务描述）
- **编排任务:** 动态规划下一步该做什么
- **执行任务:** 按任务要求完成具体工作

# Constraints

## 场景限制
- ___

## 输出格式
- ___
```

## 7. 设计实体之间的关系

```
System Prompt（全局唯一）
 │  "你是谁、什么约束"
 │
 ├── AOM 层级 1 ──── Middleware（标准动作 + 绑定 Skill/Tool）
 │    │               State（本层新增字段）
 │    │
 │    ├── AOM 层级 2 ──── ...
 │    │    │
 │    │    ├── AOM 叶子层 ──── Middleware（标准动作）
 │    │    │    │               State（叶子层字段）
 │    │    │    │
 │    │    │    ├── Task A ──── Handler（业务逻辑）
 │    │    │    │                扩展 State（Task 专属字段）
 │    │    │    │                Task Prompt（行为指令）
 │    │    │    │                Skill（方法论知识）
 │    │    │    │                Tool（可执行动作）
 │    │    │    │                Card（展示卡片）
 │    │    │    │
 │    │    │    ├── Task B ──── ...
 │    │    │    └── Task C ──── ...
```

### 各实体的核心区别

| 实体 | 给谁看 | 什么时候 | 内容是什么 |
|------|--------|---------|-----------|
| **System Prompt** | LLM | 始终 | 你是谁，你的约束 |
| **Task Prompt** | LLM | 任务启动时 | 这个任务怎么做 |
| **Skill** | LLM | 任务启动时 + 按需查阅 | 做这类事情的方法论 |
| **Tool** | LLM 调用 → 框架执行 | LLM 决定时 | 可执行的动作 |
| **Card** | 前端渲染 + LLM 看 description | Tool 触发时 | 用户看到的界面内容 |
| **AOM State** | 框架内部 | 贯穿全程 | 各层的运行数据 |

### Skill vs Tool vs Task Prompt 的区分原则

| | Skill | Tool | Task Prompt |
|---|-------|------|-------------|
| **本质** | 知识文档 | 可执行函数 | 行为指令 |
| **格式** | Markdown | Python @tool | Markdown |
| **LLM 用法** | 阅读，指导决策 | 调用，执行动作 | 阅读，遵循步骤 |
| **复用性** | 跨 Task 复用 | 可跨 Task | 每个 Task 一份 |
| **举例** | "如何做兴趣探测" | `search_customer_info(id)` | "你正在做需求挖掘任务，步骤是..." |
